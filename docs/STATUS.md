# Capability status

What works, what partly works and what is unverified, with the evidence behind each statement.
"Real input" means official public builds (PX4 v1.17.0, ArduPilot bootloaders, ArduPilot SITL
vehicle builds, Betaflight and INAV release builds), root filesystems exported from official
Debian/Alpine images, or esptool's published ESP images — never synthetic data. Numbers come from actual runs in the development environment
(2026-11-04/05).

## Fully working (verified with real inputs and covered by tests)

| Capability | Evidence |
|---|---|
| Upload → isolated analysis → report, end to end | Real PX4 FMUv5 `.px4` scan through the broker: built-in scanners, OSV, FwAnalyzer, cwe_checker, Ghidra and FACT all completed (8 findings, 31 min). ArduPilot CubeOrange bootloader and PX4 CAN bootloader: all applicable engines completed. |
| Compose stack from the published Dockerfiles | `docker compose build` of `docker/sandbox.Dockerfile` and `docker/app.Dockerfile` (proxy CA as a build secret); real scans of PX4 `.px4` (v1.15.0 and v1.17.0) and unstripped ELF, Debian/Alpine root filesystems, ArduPilot and INAV builds through the containerised broker with an unprivileged worker (PX4 v1.15.0 FMUv5: OSV, FwAnalyzer on the extracted `/etc`, cwe_checker 3/3 and Ghidra 3/3 binaries in 22 min); scan deletion removes directory, upload and pinned input. |
| Docker isolation without Docker access in API/worker | Broker is the only Docker client; verified with an unprivileged (uid 10002) worker and a containerised broker (no network, read-only, minimal capabilities). Worker cannot rename scan directories, create links in the work root or swap the mounted upload (pinned hard link in `work/.inputs/`). |
| Scan directories treated as hostile by worker and API | No planted link is followed, FIFOs and oversized files are rejected, worker-written files replace planted links (`dfa/safefs.py`); the broker strips links/special files on hand-back. A planted `findings.json -> dfa.db` overwrote the database before the fix. Every sandbox-produced finding is type- and enum-checked, strings that are not UTF-8 are escaped, `NaN`/`Infinity` in containers and tool output parse as null (a `.px4` with `"board_id": NaN` made its scan unviewable), and the UI links only http(s) references (`tests/test_api.py`, `tests/test_safefs.py`, `tests/test_sandbox.py`). |
| Container hardening and limits | `--network none`, read-only rootfs, `cap-drop ALL`, `no-new-privileges`, memory/CPU/PID/fsize limits, timeouts, per-scan disk cap, non-root UIDs (`tests/test_sandbox.py`, real Docker runs). |
| Extraction safety | Traversal, links, devices, bombs, nesting, ext duplicate-entry attack, CROMFS loops, file names that are not UTF-8 (before the fix one such name in a tar failed the whole scan, and one in a zip flagged UTF-8 left the entire zip unextracted). Content cannot be hidden behind a tar end-of-archive marker or damaged header (concatenated tars), behind 0xFF flash padding after a gzip/xz/zstd stream (which made the whole stream fail), in the later archives of an initramfs (concatenated cpio), after a uImage payload (sysupgrade-style root filesystem) or after a SquashFS image (OpenWrt's overlay), or in ext entries with quotes, newlines or non-UTF-8 bytes (listed and dumped by inode now); data after a stream or image that is not padding is analysed as an artifact of its own. A property test with generated hostile tar/zip archives (`tests/test_extract_security.py`). |
| PX4 identification and extraction | FMUv2/v5/v6X `.px4` (v1.15.0, v1.16.2, v1.17.0), CubeOrange, Kakute H7, FMUv6C, CAN bootloader, unstripped ELF: platform, version, board ID and name, build commit and time, Cortex-M architecture, flash base; NuttX CROMFS `/etc` extracted (fixed on real builds: FMUv2's end-of-list offset and v1.15.0's "threaded" directory lists). The flash image derived from the FMUv2 ELF is byte-identical to the image in the official `.px4` (`tests/test_formats_real.py`). |
| ArduPilot identification | Official AP_Bootloader builds (fmuv3, Matek H743, Pixhawk 6X, CubeOrange `.bin`/`.hex`) → ArduPilot / AP_Bootloader. SITL vehicle builds → ArduCopter 3.2.1 (`ArduCopter V3.2.1`), ArduCopter 3.3 (`APM:Copter V3.3`), ArduPlane 3.3.0, ArduRover 2.50 (`ArduRover v2.50`), all high confidence; vehicle-specific OSV tags (`APMrover2-2.50`, `ArduPlane-3.3.0` match CVE-2026-38971 as `unverified`). |
| Betaflight / INAV identification | Official release builds (Betaflight 4.3.2 STM32F405/H743, INAV 7.1.2 Matek F405/H743, INAV 6.1.1 Matek F405): platform (high confidence), version, board/target, git revision and build date from the projects' build-information block, Cortex-M architecture and flash base. Fixed on these builds: no version extracted, INAV only "medium" confidence, and F405 images with the stack in CCM RAM (`SP = 0x10010000`) not recognised as Cortex-M. OSV has no records for either project. |
| cwe_checker | ARM and AArch64 ELF (Debian/Alpine binaries, CWE-676 on `strcpy` user); bare-metal Cortex-M (PX4 image/IO/bootloader, ArduPilot bootloader); unstripped Cortex-M ELF via its derived flash image, with results mapped to the ELF's function symbols (PX4 FMUv2: 101 warnings in 57 functions). | Ghidra headless layer | Function recovery on ELF (2,500–2,660 functions for perl/libc/bash; 6,366 for the PX4 FMUv2 ELF) and raw Cortex-M images seeded from the vector table (PX4 8,258 functions; ArduPilot bootloader 331). |

PX4 NuttX `/etc` with drone rules (matched the `CBRK_SUPPLY_CHK` overrides the built-in scanner found). |
| FACT integration (REST) | Real FACT_core instance: upload, status polling, result retrieval, per-file details. Debian 11 rootfs: completed in 222 s (3,311 files). Files extracted from PX4's CROMFS are submitted as a tar (72 files analysed). Found and fixed on real output: keep-alive resets, per-file cwe_checker slowness, re-submissions misread, over-reported credentials/weaknesses, stored results of plug-ins not requested, GnuTLS self-test keys reported as leaked keys, file count. |
| Package inventory and backport-aware matching | Debian 11 (96 packages) and Alpine 3.15 (14) parsed; distro advisories matched against exact installed versions (e.g. `libssl1.1 1.1.1k-1` → DLA-3942-1, fixed in `1.1.1n-0+deb11u6`). |

## Partially working

| Capability | Limitation |
|---|---|
| cwe_checker bare-metal mode | Experimental upstream and slow: 8 minutes for the 1 MB FMUv2 image, about 20 for the 2 MB FMUv5 image. The Cortex-M ELF itself still crashes cwe_checker 0.9.0 (upstream bug), which is why the derived image is analysed. |
| FACT on MCU firmware | FACT cannot unpack `.px4`, raw MCU images or NuttX CROMFS; the decoded images and the extracted CROMFS files are submitted too, but none of FACT's plug-ins finds anything in PX4 content (reported as such). |
| ArduPilot board firmware (`.apj`) | Container parsing and ChibiOS board builds are covered by synthetic samples only: `firmware.ardupilot.org` is blocked by the development environment's network policy, and building ArduPilot from source there was not permitted. Vehicle/version identification itself is verified on the SITL builds. |
| FwAnalyzer | Permission checks need original metadata: available for tar, ext, SquashFS (read with `unsquashfs -lln`: unprivileged extraction, as in the sandbox, drops setuid/setgid bits) and Unix-made zip root filesystems (cpio permission image); other trees (ROMFS, zips without Unix modes) run without them. Owners are lost for JFFS2/UBIFS/EROFS trees extracted in the sandbox (EROFS keeps setuid/setgid bits). ext image mode panics with stock e2tools, so the permission image is used instead. |
| Upstream (non-distro) component matching | Version strings matched to OSV GIT release tags and to the affected-version ranges published with each CVE (range and source shown per match). Vendor backports, and whether the affected code is even built in (e.g. a NuttX host tool or example), are invisible, so always `unverified`. |
| Ghidra risky-call findings on MCU images | Library calls are recognised by name, so stripped raw images yield function statistics but no call-site findings (the report says so). ELF builds with symbols (PX4 ELF) are analysed with names. |
| DJI / Parrot | Headers parsed from public community documentation; DJI encrypted modules are reported, never decrypted; no real vendor samples used. |
| Additional formats: LZ4, Zstandard, lzop, CramFS, EROFS, Android sparse, UBI/UBIFS, JFFS2, SquashFS, ext2/3/4, FAT | Extraction is verified with images produced by the reference tools (`lz4`, `zstd`, `lzop`, `mkfs.cramfs`, `mkfs.erofs`, `img2simg`, `mkfs.ubifs`/`ubinize`, `mkfs.jffs2`, `mksquashfs`, `mkfs.ext4`); no real drone firmware in these formats was available. UBI/UBIFS, JFFS2 and EROFS are only unpacked inside the sandbox container. |

## Unverified

| Capability | Why |
|---|---|
| gVisor (`DFA_SANDBOX_RUNTIME=runsc`) | Configuration support exists, and the broker refuses jobs if the runtime is not registered with the daemon; installing runsc in the development environment was not permitted. |
| Rootless Docker / Podman for the broker | Documented (`docs/SECURITY.md`), not tested: the development host uses cgroup v1, where rootless Docker cannot enforce the memory/CPU/PID limits. The broker now refuses jobs on any daemon that reports it cannot enforce them (`tests/test_sandbox.py`). |
| FACT reached from the compose network | Compose maps `host.docker.internal` for `DFA_FACT_URL`; the development FACT listens on loopback only, and exposing it to the container network was not permitted. The adapter itself is verified against that FACT instance. |
